# 聊天界面的移动端软键盘适配

研究及实现维护日期：2026-10-15。文档区分公开资料结论、项目实现和实际验证范围。

## 1. 案例入口

| 入口                         | 地址                            | 用途                                               |
| ---------------------------- | ------------------------------- | -------------------------------------------------- |
| 说明与高度模拟               | `/?scene=keyboard`              | 桌面模拟键盘占用 0–320px，观察消息滚动与输入框增高 |
| 独立聊天页                   | `/?scene=keyboard&standalone=1` | 手机浏览器顶层页面，实际点击输入框拉起键盘         |
| 实验台内选择「聊天与软键盘」 | `/?scene=lab`                   | 组合观察宽度变化；iframe 不能代替真实键盘测试      |

案例中的联系人消息均为本地教学数据，不接入聊天服务。草稿与消息只保存在当前组件内存里；调整高度保留状态，刷新或离开页面会重置。

## 2. 问题与资料结论

布局视口负责页面布局，可视视口表示当前真正可见的区域。软键盘可能只缩小可视视口，也可能同时缩小布局视口，或覆盖页面而不缩小任一视口。不能仅凭 `position: fixed; bottom: 0` 保证输入栏位于键盘上方。[1][2]

`dvh` 主要响应浏览器动态工具栏。默认键盘行为下，它不保证随软键盘缩小；仅将 `100vh` 改成 `100dvh` 不是完整方案。[3]

高度变化也可能来自旋转、地址栏和捏合缩放。因此本例展示测量值，不将“高度差大于某阈值”宣称为可靠键盘检测。[2]

## 3. 可选方案与本例选择

| 方案                                 | 适合情况                                   | 本例处理                                   |
| ------------------------------------ | ------------------------------------------ | ------------------------------------------ |
| `dvh` + 内部滚动                     | 动态工具栏、浏览器已缩小布局视口           | 作为其他场景的基础，不单独承担键盘处理     |
| `interactive-widget=resizes-content` | 支持该 meta 配置的浏览器，让布局视口也缩小 | 记录为可选方案，没有修改项目全局 meta      |
| VisualViewport                       | 顶层窗口的可视区域实际改变                 | 独立页的主要实现，测量高度、宽度和偏移     |
| VirtualKeyboard API                  | 需要主动接管覆盖行为且目标环境支持         | 未启用；需要另行评估兼容性和安全上下文要求 |
| 原生 / WebView 桥接                  | 容器使用原生键盘策略、网页拿不到遮挡信息   | 不在本次案例范围内                         |

`interactive-widget` 的 `resizes-visual`、`resizes-content` 和 `overlays-content` 分别表达只缩可视视口、调整布局视口、覆盖内容；应按目标浏览器测试支持情况。[4]

VirtualKeyboard API 的能力和支持范围不能等同于 VisualViewport；本例不设置 `navigator.virtualKeyboard.overlaysContent`。[5]

## 4. 页面结构

```text
聊天外壳：跟随有效可视区域
  ├─ 标题与操作：auto
  ├─ 消息列表：minmax(0, 1fr)，内部滚动
  └─ 输入栏：auto，文本框允许增高
```

核心布局在 `src/styles.css` 的 `.keyboard-chat`：

```css
.keyboard-chat {
  height: 100%;
  display: grid;
  grid-template-rows: auto minmax(0, 1fr) auto;
  overflow: hidden;
}

.keyboard-message-viewport {
  min-height: 0;
  overflow-y: auto;
  overflow-anchor: none;
  overscroll-behavior-y: contain;
}
```

标题和输入栏不单独 fixed，消息区负责收缩。输入框最多占聊天高度的四分之一或 8rem，超出后在输入框内部滚动。极端矮屏、大字号环境仍需实机检查可操作空间。

新案例的字号和间距主要使用 rem；实际视口测量按 API 返回的 CSS px 写入容器尺寸。单位承担不同职责，没有按键盘高度缩放根字号或整页内容。

## 5. 可视区域同步链路

阅读 `src/core/visualViewport.ts` 与 `src/scenarios/KeyboardScenario.vue`：

1. 初始读取当前窗口 `visualViewport`，缺失时降级为 `innerWidth / innerHeight`。
2. 监听 VisualViewport 的 `resize / scroll` 和窗口的 `resize`，用 requestAnimationFrame 合并同一帧的更新。
3. 独立聊天外壳 fixed 定位：`height / width` 采用可视尺寸，`top / left` 采用 `offsetTop / offsetLeft`。
4. 不再从可视高度中额外扣除一次“键盘高度”，避免双重压缩。
5. 捏合缩放时仍更新观测数据，但冻结聊天外壳的尺寸与定位，交给浏览器自然缩放和平移；恢复比例 1 后重新同步。这是本案例的产品策略，不是 API 的强制要求。
6. 独立页挂载时锁定页面外层滚动，卸载时恢复之前的 overflow；同时清理视口监听和未执行的动画帧。

高度或宽度短暂为零时不覆盖最后一次有效测量。API 缺失时的 innerHeight 降级不保证解决覆盖式键盘。如果键盘不改变任何视口，本方案无法仅凭视口数据知道实际遮挡范围。

只有顶层窗口的可视视口与布局视口存在有用的区别，iframe 的对应数据通常等于其布局视口。[2] 因此模拟面板通过明确的高度滑块观察重排，实机入口使用独立顶层页面。

## 6. 消息滚动与焦点

阅读 `src/core/messageScroll.ts` 与 `src/components/KeyboardChat.vue`：

| 触发                      | 原本跟随底部 | 正在阅读历史                               |
| ------------------------- | ------------ | ------------------------------------------ |
| 键盘开合 / 消息区高度变化 | 重新贴底     | 保持原 scrollTop，允许浏览器合法范围内钳制 |
| 输入框多行增高            | 重新贴底     | 保持原 scrollTop                           |
| 模拟来信                  | 展示最新消息 | 不跳底，累加未读数                         |
| 主动发送 / 点回到底部     | 展示最新消息 | 主动恢复跟随并清空未读                     |

距离底部不超过 40px 被视为仍在跟随，这是案例自定义容差。ResizeObserver 同时观察消息视口与内容，以应对输入区挤压和内容高度变化；高度改变造成的滚动事件不直接视为用户离开底部。

本策略用于追加消息，不实现向上加载历史、虚拟列表或跨字号变化的消息锚点恢复。保留数值 scrollTop 不等于在所有换行重排后保留同一条消息。

文本框支持多行输入，Enter 换行，发送按钮提交，不注册可能干扰中文输入法的 Enter 发送快捷键。页面打开时不自动聚焦，发送后再恢复输入焦点。真实触屏上的键盘是否保持展开由浏览器共同决定，需实测。

输入框使用至少 16px 的字号，保留浏览器缩放。输入栏与标题留安全区间距；安全区不是键盘高度，也不重复叠加键盘占用。

## 7. Windows 开发环境连接手机

本项目默认仅监听 `127.0.0.1`。手机与电脑连接同一局域网后，先停止本项目原来的开发服务，再在 Windows PowerShell 中启动：

```powershell
cd C:\code\shadcn-vue-responsive-lab
npm run dev -- --host 0.0.0.0
```

按 Vite 输出的 Network 地址，将路径改为 `/?scene=keyboard&standalone=1`，在手机浏览器中直接访问。Windows 防火墙须允许对应的 Node 开发服务入站。手机的 `127.0.0.1` 指向手机自己，不能用它访问电脑。

这次维护没有改变正在运行服务的监听地址。普通源代码更新通过 Vite 热更新即可；要启用局域网访问才需要按上面方式重启。

以下均为直接维护 API 或浏览器的官方文档，2026-10-15 查阅。Chrome 文章发布于 2022 年，说明 Chrome 108 的行为变更；其中历史浏览器分类和当时兼容情况不能当成所有浏览器的当前完整支持矩阵。

4. [MDN：meta viewport](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport)：interactive-widget、缩放和安全区配置。
5. [MDN：VirtualKeyboard API](https://developer.mozilla.org/en-US/docs/Web/API/VirtualKeyboard_API)：主动控制键盘覆盖布局的另一条路线及能力限制。
