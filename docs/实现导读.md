# 从源码理解手机与桌面适配

## 1. 先区分三类机制

| 需求                         | 本工程使用                            | 原因                              |
| ---------------------------- | ------------------------------------- | --------------------------------- |
| 间距、列数、位置、按钮显隐   | CSS 媒体查询、Tailwind 响应式类       | 不需要为样式添加 JS 状态          |
| 手机抽屉与桌面侧栏是不同容器 | `useMediaQuery` + Vue `v-if / v-else` | 模态层、Portal 和布局占位职责不同 |
| 同一组件可用空间随侧栏变化   | CSS Container Query                   | 浏览器窗口没变，但主区宽度变化了  |

`App.vue` 持有当前场景和全局侧栏状态，向子组件提供上下文。`ResponsiveSidebar.vue` 只负责按断点选择容器。`SidebarContent.vue` 负责共享菜单内容。

## 2. 侧栏两端状态为什么分开

在 `src/core/sidebar.ts` 中：

- `desktopOpen` 保存电脑侧栏展开偏好，写入 localStorage。
- `mobileOpen` 只表示手机抽屉是否打开，刷新后初始关闭。
- `toggle()` 根据 `isMobile` 操作不同状态。
- `closeOnDesktop` 是教学新增策略，不是默认上游行为。开启后，进入桌面时清空手机开关。
- `events` 记录状态变化与菜单挂载 / 卸载，让链路可以直接观察。

测试中用一个真实的响应式 `Ref<boolean>` 驱动断点，而不是改 UA 或重建应用。

### 场景 A：保留手机状态

```text
手机打开抽屉
  mobileOpen = true，desktopOpen 保持原值
       ↓ 视口达到 768px
卸载 Dialog 分支与 Portal
创建桌面 fixed + gap
  desktopOpen 决定展开 / 收起
       ↓ 再回到窄屏
重新创建 Dialog，mobileOpen 仍为 true
抽屉恢复打开
```

### 场景 B：进入桌面时关闭手机抽屉

同一链路，仅在进入宽屏时加一步 `mobileOpen = false`。再次缩回手机时抽屉保持关闭。这个策略改善的是临时 UI 状态，不应该顺便修改桌面偏好。

### 注意：点击导航与跨断点不是同一事件

点击菜单项会调用 `closeMobileOnNavigate()`。因此用户主动导航后，抽屉已关闭，后续缩回手机也不会重新打开。

## 3. 宽屏为何需要 gap

`position: fixed` 元素不占文档流空间。如果只有固定侧栏而没有正文左边距或占位机制，正文会被侧栏覆盖。

本例使用单独的 gap 承担布局占位职责，实际菜单层承担固定定位、内容滚动和交互职责。两者职责不同，不是无意义 DOM。

- 展开：gap 和侧栏同宽。
- 图标收起：两者均变为 72px。
- 完全收起：gap 变为 0，实际侧栏移出左边界。
- 样式根据 `data-state` 和 `data-mode` 切换，不依赖 JS 每帧计算宽度。

## 4. 手机为何使用 Dialog

Reka Dialog 提供 Portal、模态语义、焦点管理及关闭行为，CSS 再把它呈现为左侧抽屉。

- 遮罩和菜单 fixed 定位，不参与主区宽度分配。
- 导航点击、遮罩点击、Escape、显式关闭按钮均可退出。
- `v-if` 分支切换时，Portal 跟着旧分支卸载，不应把遮罩留在桌面。
- 正常打开抽屉有进入动画；跨分支不额外编排动画。

`ResponsiveSidebar.test.ts` 的测试会挂载真实 Reka Dialog，检查手机打开后存在 dialog / overlay，切桌面后两者消失，重新切回手机可恢复。

本工程没有照搬上游对 `body[data-scroll-locked]` 的全局覆盖，避免教学案例无意绕过弹层库的模态滚动管理。实际滚动与软键盘表现仍需要实机检查。

## 5. 聊天业务与显示状态分离

`selectedId` 决定当前业务会话；`mobileDetailOpen` 决定手机是否展示详情。

- 点会话：设定业务 ID，打开手机详情。
- 手机返回：只关闭详情。
- 拉宽：CSS 把详情从绝对定位改为正常流，与列表并排。
- 所有消息与草稿在同一实例中，不同时挂载两份聊天组件。

没有把 `mobileDetailOpen` 设计成路由。浏览器返回键不会自动变成详情返回；如果生产应用需要链接分享、前进后退，应使用真实路由承载会话 ID。

## 6. 容器查询解决什么问题

`ContainerScenario.vue` 声明 `container: sample / inline-size`，在 CSS 中使用：

```css
@container sample (min-width: 480px) {
  .metric-grid {
    grid-template-columns: repeat(2, minmax(0, 1fr));
  }
}
@container sample (min-width: 720px) {
  .metric-grid {
    grid-template-columns: repeat(4, minmax(0, 1fr));
  }
}
```

480 / 720px 在此是容器内容区宽度，不是浏览器视口。组件的 padding 和边框会影响能容纳多少内容；页面同时显示 `useElementSize` 观测值，以真实空间为准。

`useElementSize` 只显示数值，不参与卡片列数判断。可以关闭 JS 观测逻辑，CSS 仍会按容器宽度生效。

## 7. 同一模态框与切换模态容器的区别

- 侧栏：`v-if` 更换 Dialog 和 aside，菜单内容实例会重建。
- 产物：更换桌面 aside 与全屏 Dialog，但主聊天不变；预览内容抽成共享组件。
- 新建项目弹层：始终是同一个 Dialog，只切换 CSS 位置。输入中的表单数据自然保留。

这是三个不同案例，不应都称为「把桌面页面缩小」。

## 8. 断点和高度边界

| 模块     | 查询                                        |
| -------- | ------------------------------------------- |
| 全局侧栏 | `<48rem` 为抽屉，默认 768px                 |
| 聊天单屏 | `<40rem` 为单屏，默认 640px                 |
| 设置导航 | `<768` 下拉、`768–1023` 横排、`>=1024` 纵排 |
| 产物并排 | `>=80rem`，默认 1280px                      |
| 指标卡片 | 容器内容区 480 / 720px                      |

整页使用 `min-height: 100svh`，抽屉与全屏预览使用 `100dvh`。输入不使用绝对定位贴到一个写死的屏幕高度。安全区采用 `env(safe-area-inset-bottom)`。

这些设置不能替代真实 iOS / Android 的键盘测试。此工程未声明已解决所有软键盘、浏览器地址栏和内嵌 WebView 差异。

新增「聊天与软键盘」案例专门研究纵向可视区域：说明页提供高度模拟，独立页通过 VisualViewport 测量并调整外壳。消息列表承担滚动，输入栏始终留在三行 Grid 的最后一行。实现细节、适用边界及资料来源见 [聊天软键盘适配](聊天软键盘适配.md)。原聊天列表 / 详情案例仍用于宽度与业务状态教学。

## 9. 代码阅读顺序

1. `src/core/breakpoints.ts`：断点与场景。
2. `src/core/sidebar.ts`：状态、偏好、策略、日志。
3. `src/components/ResponsiveSidebar.vue`：分支切换。
4. `src/components/SidebarContent.vue`：共享菜单、导航关闭、生命周期。
5. `src/styles.css`：fixed + gap、抽屉、媒体和容器查询。
6. `src/scenarios/FramePlayground.vue`：真实 iframe 视口实验台。
7. `src/core/sidebar.test.ts` 和 `src/components/ResponsiveSidebar.test.ts`：关键状态和 Portal 链路。
8. `src/scenarios/KeyboardScenario.vue`、`src/components/KeyboardChat.vue`：键盘模拟与独立聊天页。
9. `src/core/visualViewport.ts`、`src/core/messageScroll.ts` 及对应测试：视口监听、清理和滚动策略。
